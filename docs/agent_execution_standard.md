# 代理执行规范

本项目采用固定分工，确保判断、操作和验收可追溯。

## 角色

| 角色 | 固定模型与职责 | 不执行的事项 |
|---|---|---|
| 主进程 Sol | 研究判断、任务排序、风险决策、结果验收和对作者的结论说明 | 不直接运行命令、不改文件、不直接连接服务器 |
| Luna subagent（5.6 Luna） | 文件编辑、脚本执行、测试、远端预检、上传、启动、回传和报告渲染 | 不擅自改变物理范围、验收阈值、停止策略或论文结论 |

## 工作流程

1. Sol 明确问题、物理范围、资源预算和验收门。
2. Luna 将参数、路径和非覆盖策略写入可审计记录，完成只读预检。
3. Luna 执行已授权操作，并立即记录 PID、日志、进度文件和输入哈希。
4. Luna 运行本地 QA，将原始事实交回 Sol。
5. Sol 根据验收门决定接受、隔离、补算或降级；Luna 再执行对应操作。

## 必须遵守的边界

- 物理范围固定为 `0 <= alpha,beta <= 1`；永久排除负 alpha 与参考 Fig.9。
- 不在未授权情况下写入 `paper/`，HTML 报告是当前唯一可编辑论证载体。
- 远端重任务必须使用独立目录、拒绝覆盖、离线 Julia 环境、`progress.json`、`status.json` 和终态 checksum。
- 运行中只做约定的一次启动核验；不反复轮询。终态按 checksum、非覆盖回传、validator、accepted-only 组装、CV--TEBD 重分析的顺序处理。
- 若已有重型 Julia，额外并行任务须由 Sol 先基于 CPU、内存、磁盘和优先级决定；Luna 只按指定线程和 nice 上限执行，禁止自行扩容。

## 计算安排与 ETA

- 每次计算启动前，Luna 必须记录任务目的、参数、资源上限、输出目录、验收门和初始 ETA。
- 每次计算必须在 ETA 创建一次性只读检查；检查只读取 `status.json`、`progress.json`、PID、资源、stderr、manifest 和 checksum。
- 未终态时只记录资源和更新后的条件 ETA，禁止高频轮询、禁止新增 Julia；终态时才进入既定验收和回传链。
- 一次性检查同样遵守 Sol 决策、Luna 操作，以及 `0 <= alpha,beta <= 1`、排除负 alpha 和 Fig.9 的范围。
